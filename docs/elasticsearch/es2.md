# 整体方案选型结论
业务是**蓝领招聘岗位搜索**，你的4个痛点：【缺检索字段、无兜底召回、结果上限30、排序不符合自营优先、缺少筛选】
✅ 推荐：**Elasticsearch（ES）作为主检索引擎**，搭配多策略召回 + 业务重排 + 兜底召回 + 筛选聚合，是这类招聘平台最成熟落地方式；
> 不推荐纯MySQL like：字段多、分词差、排序权重难控、聚合筛选性能差，空结果兜底很难做；
> 不推荐向量检索为主：你当前核心是**文本关键词岗位检索**，向量适合语义扩词，做辅助增强，不能当主力。

下面分：**检索能力改造、召回策略、排序规则、筛选能力、空结果兜底、架构、配套技术、落地优先级**，贴合你蓝领招聘场景。

## 一、检索字段改造（解决【搜不到品牌】）
原来只搜：岗位标题、营业执照名称、二级类目
👉 扩展检索字段，在ES建立**多字段索引，区分权重**（重点把品牌字段加进去）
| 字段 | 权重 | 分词策略 | 说明 |
| ---- | ---- | ---- | ---- |
| 岗位标题 | 最高 boost=10 | 中文分词（ik_max_word） | 核心关键词 |
| 品牌名称 | boost=8 | ik，支持全称/简称匹配 | 你现在缺的，用户直接搜品牌 |
| 公司名称（执照） | boost=6 | ik | 原有 |
| 一级类目、二级类目 | boost=4 | ik | 类目词 |
| 岗位标签、岗位描述、薪资标签、工作地点 | boost=2 | ik | 弱匹配，补充召回 |

> 分词器：**IK分词器**（蓝领关键词：操作工、日结、临时工、富士康这类短词适配好）；
> 进阶：同义词词典维护：比如 `富士康 ↔ 鸿海`、`美团 ↔ 美团骑手`，品牌别名统一召回。

检索语法：`multi_match` 多字段检索，按上面boost加权，不是均等匹配。

## 二、召回策略（核心解决：搜不到 + 空结果流失）
两层召回：**精准召回（主） + 语义扩词/模糊召回（兜底）**
1. **第一路：关键词精准召回（默认优先）**
   用户输入词 → multi_match 加权检索（标题、品牌、公司、类目）
2. **第二路：兜底召回（当第一路结果为空 / 条数太少时触发）**
    - 同义词扩词召回（同义词词典）
    - 模糊fuzzy召回（允许少量错别字，比如“富土康”匹配富士康，fuzziness=1）
    - 类目兜底：提取用户输入里面的类目词，返回该类目下热门岗位（最重要！解决空页流失）
    - 可选轻量语义召回：使用Embedding（bge-small）做向量相似度召回，作为补充，**放在最后兜底**
> 逻辑：
> 精准召回 ≥1条 → 走正常排序；
> 精准召回=0 → 启动兜底多路召回，合并去重，给用户推荐相关岗位，不再展示空白页。

## 三、分页条数：解决【看不全，最多30条】
ES 默认无硬上限，改掉原来业务层写死30的限制：
- 前端：支持分页，pageSize可配置（比如一页20，支持翻页）
- 注意：**深度分页坑**，不要直接 from+size 翻很深；
  方案：业务普通翻页 → `search_after`；不支持无限翻，控制合理上限（比如最多允许翻200条，蓝领用户很少翻很深）
> 区分：不是一次性返回几千条，放开分页，而不是固定30条截断。

## 四、排序改造：解决【排不好，自营岗位优先】
目标：**和首页排序规则对齐**，ES使用 `function_score` / 复合sort，顺序优先级：
1. 顶层规则：**自营岗位标记优先（boost提权）**（你的核心需求）
2. 相关性分（关键词匹配得分，最重要）
3. 业务权重：岗位上架时间（新鲜度）、岗位曝光、报名转化率、是否置顶、是否急招
4. 过滤降权：下架岗位、招满岗位直接过滤不召回
> 示例ES sort逻辑：
> 先按【是否自营】(自营=1，外包=0)降序，再按检索_score相关性降序，再按发布时间降序。
> 重点：**排序是业务重排，不是只靠ES原生相关性分**，业务标签（自营）是独立排序因子。

## 五、筛选能力：解决【筛不了，搜索页无筛选入口】
ES Aggregation 聚合能力，搜索同时返回筛选项：
蓝领招聘高频筛选项：
- 工作地点（城市/区县）
- 薪资区间
- 岗位类型：日结/长期工/临时工
- 是否自营
- 性别、年龄、包吃住
- 类目
  流程：
1. 用户搜索关键词 → ES查询 + 同步terms/range聚合
2. 后端返回【岗位列表 + 聚合筛选项】给前端
3. 前端渲染筛选面板；用户勾选筛选条件后，追加filter条件到ES query
> filter 上下文：不影响相关性打分，只做过滤，性能好。

## 六、整体技术栈清单
### 检索核心
- Elasticsearch 7.x / 8.x（推荐8.x）
- IK Analyzer 中文分词器 + 自定义同义词词典
- 索引结构：岗位主索引，定时同步（Canal监听MySQL binlog，增量同步岗位、品牌、类目、自营标记状态）
> 同步链路：MySQL(岗位库) → Canal → MQ(RocketMQ/Kafka) → ES同步服务 → ES
> 好处：岗位新增、上下架、品牌修改实时同步，延迟低；避免定时全量同步笨重。

### 兜底增强（可选，按需上）
- 向量库：ES内置dense_vector（不用额外搭Milvus），Embedding模型 bge-small-zh，做语义兜底召回
- 纠错：用户输入错别字，fuzzy模糊检索 + 热词词典（运营维护品牌热词、岗位热词）

### 后端 & 网关
- Java（你现有技术栈SpringBoot），封装ES检索服务，单独拆Search服务（解耦，独立扩容）
- 搜索服务内部：
    - 查询组装层（组装multi_match、filter、function_score排序、聚合）
    - 召回路由层：判断是否空结果，触发兜底召回、结果合并去重、去重（同一个岗位多路召回重复）
    - 结果脱敏、组装返回给前端

### 缓存优化（高频热词）
- Redis：缓存热门搜索词的检索结果、筛选项聚合，减轻ES压力；过期时间短（1~3min），岗位变化快。

## 七、两种可选方案对比（方便你评审）
| 方案 | 适合场景 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| ES主检索（推荐） | 你的场景：多字段加权、品牌检索、筛选聚合、自定义排序、空兜底 | 成熟、分词好、聚合筛选原生支持，蓝领招聘大量落地案例 | 需要维护同步链路，有运维成本 |
| MySQL+FullText全文索引 | 预算极低、体量很小 | 不用额外组件 | 分词弱、不能精细权重、聚合筛选差、兜底很难做，后期一定会重构 |

> 你现在4个痛点，MySQL全文满足不了【自营优先排序、多字段权重、聚合筛选、多路兜底召回】，直接上ES是长期最优解。

## 八、落地优先级（渐进式，不用一次性全做完）
1. P0（最快见效）
    - ES索引新增品牌字段、调整multi_match权重；同步品牌数据
    - 业务层去掉30条硬编码限制，改成search_after分页
    - 排序改造：接入自营标记优先的排序逻辑，对齐首页
2. P1
    - 搜索结果页增加ES聚合筛选（地点、薪资、是否自营）
3. P2（解决空结果流失）
    - 空结果兜底策略：类目热门召回、同义词、fuzzy纠错
4. P3 优化：热词维护、向量语义兜底、搜索埋点统计（空值率、搜索词、点击）

## 九、配套埋点（用来持续优化空搜率）
搜索服务埋点上报：
- search_keyword、召回条数、是否空结果、是否走兜底、点击岗位
  后续统计：高频无结果词，运营维护热词/同义词，持续降低空搜率。

## 补充边界提醒
1. 品牌字段要提前清洗：很多品牌有别名、简称，需要运营维护同义词库，不然用户搜简称还是搜不到；
2. 岗位状态过滤：招满、下架岗位，在query的filter里直接过滤，不要召回再剔除；
3. 多路召回合并的时候，**去重**，同一个岗位精准召回和语义兜底都召回时，只保留一条，优先保留精准召回的那条。
