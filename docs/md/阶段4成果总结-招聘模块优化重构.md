## 一、为什么要做这次重构

招聘链路（简历解析 → JD 生成 → 候选人评分 → RAG 召回）功能是通的，但代码里埋了一批**企业级高并发场景下一定会出问题**的坑。本次不做新功能，只做"修 bug + 补规范"，核心目标有三个：

1. **不占连接**：把 5~30s 的 LLM 调用从事务里挪出去，避免连接池被打满；
2. **不丢数据、不崩溃**：失败记录不能被回滚掉，评分不能因除零抛异常；
3. **接口统一**：全部收敛到项目既有的 `Result<T>` 规范，异常交给全局处理器。

改动规模：**10 个文件修改 + 5 个新增文件，+680 / -596 行**。

## 三、修复的严重缺陷（逐条：现象 → 原因 → 修法）

### 3.1 慢 LLM 调用被包在事务里 → 连接池耗尽 🔴

**现象**：并发上传/评分时，数据库连接池被占满，后续请求全部阻塞。

**原因**：`ResumeParseService.uploadAndParseResume` 等方法的 `@Transactional` 覆盖了文件落盘、PDF 解析、LLM 抽取（5~30s）全过程，一个请求从头到尾攥着一条数据库连接。

**修法**：把耗时 IO/LLM 一律放到事务**外**，只有最后的 insert/update 走短事务：

```
ResumeParseService:  文件落盘 + 解析 + LLM（无事务） → TransactionTemplate 落库（短事务）
JDGenerationService: LLM 生成（无事务）              → TransactionTemplate 落库（短事务）
CandidateScoringService: 读 + 本地打分 + LLM（无事务）→ TransactionTemplate 落库（短事务）
```

### 3.2 解析失败的简历记录被回滚掉 → 数据静默消失 🔴

**现象**：上传一个解析失败的简历，数据库里查不到任何记录，无法排查。

**原因**：catch 分支里 `resumeMapper.insert(resume)`（写入 failed 记录）后 `throw`，而方法级 `@Transactional(rollbackFor=Exception)` 把这条 insert **也一起回滚**了。

**修法**：失败记录改用**独立事务**提交，保证异常抛出后它依然存在。

```java
private void persistFailure(Resume resume, Exception e) {
    // 独立事务，不受外层异常回滚影响
    transactionTemplate.executeWithoutResult(status -> resumeMapper.insert(resume));
}
```

### 3.3 `optimizeJD` 空指针风险 → NPE 🔴

**现象**：传入不存在的 `jdId` 时直接 NPE。

**原因**：`jobDescriptionMapper.selectById(jdId)` 结果未判空就 `jd.setStatus(...)`；且同一行数据被 `selectById` 查了 3 次。

**修法**：顶部**只加载一次** + null 校验；同时新增 `feedbackType` 白名单校验（`adjust/approve/reject`），非法值不再静默落到 adjust 分支。

### 3.4 评分维度被静默丢弃 → 总分失真 🔴

**现象**：`locationScore` 算了但从没参与总分。

**原因**：`calculateDimensionScores` 计算了 `locationScore`，但 `DEFAULT_WEIGHTS` 里**没有 location 键**，`calculateTotalScore` 手写的 6 行加法里也**没有 location**。

**修法**：权重表补齐 `location`，并**改为按权重表遍历取分**（新增维度只要登记权重就自动纳入），权重之和恒为 1.00：

```
skill 0.30 | experience 0.25 | education 0.15 | project 0.10 | salary 0.10 | stability 0.05 | location 0.05
```

### 3.5 除零 → `NumberFormatException` 崩溃 🔴

**现象**：JD 薪资写成 `20k-20k`、或工作经验要求填 0 时，评分直接抛异常。

**原因**：
- `calculateSalaryScore`：`min == max` 时 `range == 0`，`diff / range` 得 `Infinity`，`BigDecimal.valueOf(Infinity)` 抛 `NumberFormatException`；
- `calculateExperienceScore`：`jdExp == 0` 时 `candidateExp / 0` 同样得 `Infinity`。

**修法**：两处加除零保护（`range<=0` 改用绝对差值衰减；`jdExp<=0` 视为满分），并抽 `scaled(double)` 先判 `Double.isFinite` 再转 `BigDecimal`，兜住残余 NaN/Infinity。

### 3.6 技能匹配恒为 0 → 评分失效 🔴

**现象**：技术栈完全对得上的候选人，技能分也是 0。

**原因**（两处叠加）：
1. 候选人侧 `Resume.skills` 存的是 **JSON 数组串** `["Java","Spring Boot"]`，JD 侧 `skillTags` 是 **逗号串** `Java,Spring Boot`，用同一个 `split(",")` 切，格式对不上；
2. 切完没 `trim`，`" Java"` 与 `"Java"` 永不相等，空串还会膨胀并集。

**修法**：统一 `tokenizeSkills()`——`[` 开头走 `JSON.parseArray`，否则按逗号切，统一 trim + 转小写 + 去空。

> ⚠️ **注意**：修好这段逻辑是必要的，但**端到端分数暂时仍不会有变化**，因为上游 ES 文档没写技能字段，详见第四节。

### 3.7 本地缓存无界 + 共享可变对象 🟠

**现象**：服务跑久了内存持续上涨；同一会话并发请求互相污染对话历史。

**原因**：`ConversationMemoryService.localCache` 是无界 `ConcurrentHashMap`，只有 Redis 有 TTL，**进程内永不淘汰**；且 `getOrLoadHistory` 直接返回缓存里的**可变 `LinkedList`**，`addMessage` 就地修改它。

**修法**：
- 改为容量有界（10000）+ 访问顺序 **LRU** + 按已有 `SESSION_TTL` **惰性过期**；
- **会话级加锁**保证"读—改—写"原子；
- 对外读取一律返回**拷贝**；
- Redis 读写放在锁**外**，避免持锁做网络 IO。

### 3.8 接口层规范问题 🟠

| 问题 | 修法 |
|---|---|
| 3 个 Controller 全部返回裸 `Map<String,Object>`，与项目 `Result<T>` 规范不一致 | 统一改 `Result<XxxVO>` / `Result<Page<VO>>` / `Result<List<...>>` |
| try/catch 吞异常，失败也返回 HTTP 200 + `success:false` | 删除 try/catch，交给 `GlobalExceptionHandler`；业务"不存在"返回 `Result.error(...)` |
| 使用 `@Autowired`（项目规范要求 `@Resource`） | 全部改 `@Resource` |
| `listResumes` 忽略 `page/pageSize` 参数、全表加载（带 `// TODO`） | 落实真分页：`pageResumeList` + XML，出参不含 `raw_content` |
| 批量接口串行 for 循环，每次含一次 LLM（N×5~30s） | `taskExecutor` 并行 + **有界信号量**（上限 8）+ 整体超时，返回 `BatchResultVO` |
| `uploadResume` 解析后多查一次库 | 服务直接返回完整 `Resume` 实体 |

## 四、API 契约变更（⚠️ 需前端同步）

响应体**外层结构变了**，需要调用方适配：

**改造前**
```json
{ "success": true, "resumeId": 12, "name": "张三", "elapsed_ms": 812, "message": "..." }
```

**改造后**
```json
{ "code": 200, "message": "Success",
  "data": { "id": 12, "name": "张三", "elapsedMs": 812, "message": "..." } }
```

要点：
- 原顶层字段 `success / resumeId / jd / resume / result / score / candidates / total / successCount / failCount / elapsed_ms ...` **全部移入 `data`**，`elapsed_ms` 改驼峰 `elapsedMs`；
- 错误由"HTTP 200 + `success:false`"改为 **`code:444` + `message`**；
- 涉及全部招聘接口：`/api/recruitment/resume/**`、`/api/recruitment/jd/**`、`/api/recruitment/scoring/**`。

## 六、后续应该如何优化、完善

按**优先级**排列，建议按序推进。

### P0 — 补齐上游断点（否则评分模块等于没用）

**`KafkaConsumerService.buildESDocument` 是当前评分偏低的真正根因。**

现在这个方法只写了 `id / contentVector / uploadTime / updateTime / status / source`：

```java
private CandidateResumeDocument buildESDocument(ResumeVectorizedEvent event) {
    CandidateResumeDocument doc = new CandidateResumeDocument();
    doc.setId(event.getResumeId().toString());
    doc.setContentVector(event.getVector());
    doc.setUploadTime(event.getEventTime());
    doc.setUpdateTime(event.getEventTime());
    doc.setStatus("待筛选");
    doc.setSource("upload");
    return doc;   // ← skills / experience / education / city / expectedSalary 全是 null
}
```

**后果**：`CandidateScoringService` 从 ES 取候选人时，`getSkills()` 为 null → 技能分恒 0；`getExperience()` 为 null → 经验分走默认 50；`getCity()` 为 null → 地点分走默认 80。**因此上一节的 3.6 虽然修对了，但端到端分数仍不会动。**

**做法**：按事件里的 `resumeId` 回查 `resume` 表，补齐 ES 文档字段（skills / experience / education / city / expectedSalary / expectedPosition / name / content）。

### P1 — 建立评估体系（没有它就无法判断"优化有没有用"）

1. **构造测试集**：100 个真实提问 + 标准答案（覆盖 FAQ、政策、岗位要求）；
2. **量化指标**：`Recall@K`（正确文档是否进 Top-K）、`MRR`（排在第几）、端到端准确率；
3. **每次改动后回归跑一遍**，看数字变化。

这是从"能跑"走向"准确率可信"的关键一步，也是当前项目最缺的一环。

### P1 — 召回链路加固（在已有混合检索基础上）

现有 `HybridRagService` 已实现向量 + HyDE + 查询改写 + 关键词 + RRF，方向正确。建议补：
- **重排序**：`DocumentRerankService` 已在，但配置里用的是 `qwen3-rerank`（`application.yml`），代码里硬编码了 `gte-rerank`，**两者不一致，需统一**；
- **元数据过滤**：先按 `doc_type / department` 过滤再做向量检索，显著降噪；
- **父子 chunk**：检索小 chunk、返回父 chunk 给 LLM，兼顾精度与上下文完整性。

### P2 — 稳定性与可观测性

- **未命中兜底**：RAG 返回"未找到相关文档"时，记录到"未命中问题表"，作为知识库补充的输入；答不上来走转人工流程；
- **限流与熔断**：LLM 调用目前只有线程池有界并发，建议叠加 Sentinel/Resilience4j 做接口级限流 + 熔断降级；
- **连接池监控**：接入 Druid 监控面板，本次改动后应能观察到"LLM 期间连接不再被占用"的改善；
- **`KafkaConsumerService` 消费失败**：目前失败仅打日志、不提交 offset 靠重试；建议补**死信队列**（`Topics.RECRUITMENT_DLQ` 已定义但未见使用）。

### P2 — 测试覆盖

- 招聘包**目前没有单元测试**。建议优先补：
  - `CandidateScoringService` 的纯计算部分（技能 Jaccard、除零分支、权重求和）——**无外部依赖，最容易写、收益最高**；
  - `LlmJsonUtil.extractJson` 的边界用例（空串、短串、无围栏、带解释文字）；
  - `ConversationMemoryService` 的并发读写用例。
- 项目已引入 `spring-boot-starter-test`，补集成测试成本不高。

### P3 — 架构演进（长期）

- **向量库**：当前 Milvus 独立部署，运维成本较高；若已用 PostgreSQL，可评估 PGVector 简化技术栈（`CLAUDE.md` 里已有此建议）；
- **简历文件存储**：目前落本地磁盘 `/tmp/resumes`（`resume.upload.dir`），生产应改 **OSS**，并让 `file_path` 存可访问 URL；
- **异步链路完整性**：`ResumeUploadEvent` / `sendResumeUploadEvent` 已定义但从未调用，要么接上，要么清理，避免"看似有、实际不通"的中间态。
